### What I learned and what surprised me

- **The approved Stop scheme was wrong, and a test said so.** `tech.md` section 3 step 4 has the page call `MIDIOutput.clear()` on Stop.
  The property test (E3) failed 6 of 8 generated cases: `clear()` drops Note Offs the engine already counted as sent, and the engine's
  flush only covers notes it still thinks sound. Separately, Chromium 141 has no `clear()` at all (`MIDIOutput` has `send` only;
  `p3-browser-probe/midioutput-probe.txt`). A second defect sat behind it: the clock map moves by a millisecond or two between batches, so a
  flush Note Off one sample after a Note On could be stamped earlier and delivered first. The scheduler now never calls `clear()` and never
  stamps an output earlier than its last send (50 ms window). The cost is up to one lookahead of notes after Stop. This departs from
  approved text, so it is ADR-0008 amendment 1, with a pointer in `tech.md`, flagged first in the pull request. The owner had already merged #24 (12:43 Paris) when I pushed the amendment to that branch, so the amendment commits ride in this pull request.
- **Playwright cannot hide a tab.** It keeps every page "visible and focused", so a background run through it would have measured
  nothing. S1's hidden-tab run starts Chromium itself and talks the DevTools protocol (`scripts/cdp.ts`); the first tab then reports
  `hidden`. The run checks that the tab was hidden for at least half the run and fails otherwise.
- **The stand-in's arrival numbers are noise, and the record says so.** In the background run the stand-in's `setTimeout` is throttled and
  its interval error reaches hundreds of milliseconds. That is the stand-in, not Web MIDI. It does show why events must not be timed by a
  page timer: the worklet-driven margins are the same hidden as visible.
- **The engine's step is 12 ticks and the tick is 192 to the quarter note (D0, open).** "Sixteenth notes at 120 BPM" in the plan is 30 BPM
  on the engine as it is, and 120 BPM is a step every 31 ms. S1 reports the step length it measured and runs both.
- Worklet scope: `performance` is absent, so S2 times the same module on the main thread and, in batches, with `Date` in the worklet.

### Numbers (this container: 2 cores, headless or xvfb Chromium 141, a null audio sink)

- S2 (`handoffs/evidence/p3-s2-run.txt`): five golden hashes and both pressed programs equal native, in the worklet and on the main thread;
  0 allocations in `render` in both; a 128-frame block costs about 2 us against a 2667 us budget (p99 10 us, max 525 us on the main thread).
- S1 here (`p3-s1-here-bpm30-*`, `-bpm120-*`): 0 late events in about 4,000; margin median 66 ms with a 30 ms lookahead, worst 36.8 ms (the

- **Not measured:** Web MIDI arrival jitter, which needs a real port. The kill criterion cannot be evaluated until the owner runs
  `apps/web/spikes/s1/page.html` on a Mac with the IAC Driver. Say so wherever S1 is quoted.

## 2026-10-01, later: SPEC-0002 P3c, the first panel

Task WENGE-0014, P3c. Hat: **Forge**, with **Curator** and **Conductor** hats for the tokens (marked in the commit messages: `conductor+curator:`),
and a **Referee** hat for the baseline (`forge+referee:`). Built on the P3b branch, so it carries P3b's commits (merge #25 first).

**Intend to change:** draw the first panel in a browser (the 160 matrix keys, the ten controls the controller acts on, and `transport.play`) from the
control inventory and a new tokens contract, wire it to the engine and to one Web MIDI output, and make every colour, length and type size come from
the tokens file.
**How I'll know it worked:** E1, E2, E7 and E8 pass in Chromium (a press lights a key green and a second turns it off; Play gives a fake output a Note On with
the bytes the same engine gives in Node, then a Note Off, stamped ahead of now; without Web MIDI the app loads, runs and says so; every control has the
manual's name and Tab follows the layout); the tokens contract test passes and can be seen to fail on a document made to break each rule; E9, `verify` green with the baseline only grown.

### What happened

- **Tokens first.** `apps/web/engine/tests/tokens.rs` was written before the file: 16 of 19 failed (`p3c-tokens-red-run.txt`); the three that passed are the colour
  arithmetic, and my CIEDE2000 reproduces four pairs of the published test data. The first values I picked passed every rule, which is the thing to be suspicious of, so
  every rule also runs against a document made to break it (19 tests, 16 of which are those).
- **Panel modules, red first.** Layout, tokens to CSS, press handling and MIDI access were written as tests and failed on missing modules
  (`p3c-panel-modules-red-run.txt`); then the modules. The Chromium tests were written against a page that did not exist (`p3c-browser-red-run.txt` is the same file
  rerun without the page).
- **The Chromium tests passed in their second run.** The first run found two mistakes of mine in the tests, not in the page: Playwright clicks the middle of a control's
  bounding box, which for a key with a label beside it is the gap between them (the SVG took the click), so tests click the key's circle; and the engine lights PLAY
  and EDIT green from the first frame, so "only the pressed key is lit" is about the matrix.
- **Mutation run:** 72 breakages, 65 caught at once, 7 survived, each survivor closed by a test (`p3c-mutation-run.txt`). The survivors were all the same kind: a
  property true by construction of the current layout (labels never reach past the matrix, so their width does not matter), or true of a state nobody looked at (the ring's
  radii, Space's default action). Each now has an assertion that says what it is for.
- **Screenshots** (`p3c-panel-*.png`, from `npm run screenshot`): the idle panel, a running panel with a pattern, a flashing PLAY and a focus ring on a lit key, and a 2x
  detail of the controls. They are what the owner ratifies the tokens with.

### What I learned and what surprised me

- **A contract test in Rust is a ratchet, and one in Node is not.** `cargo xtask baseline` reads `cargo test` output, so putting `tokens.rs` and
  `app_source_rules.rs` in the `octoweb` crate floors 33 tests by name where the same tests in Node would be one deleted file from gone. The Node and Chromium tests are still
  unfloored (Referee request).
- **Writing the tokens exposed a hole in the contract.** The focus ring is 2 px with a 1 px inner stroke (`docs/05` section 5), and neither is on the space scale, whose smallest step
  is 4. Without a place for them the stylesheet would hold two literals, which is what the contract exists to stop. So a `stroke` group, `flash.duty_percent` and `flash.shine`
  (ADR-0008 amendment 2). It is a finding about the ADR and not an obstacle to be worked around in the stylesheet.
- **`#000000` is within ΔE 3 of `#0b0b0b`.** The first `focus.inner` I reached for was black, and rule S8 (applied through CIEDE2000, where small steps near black count for more than a
  difference of lightness suggests) said no. The values are in the range the rule leaves, and none was chosen to dodge it.
- **A flashing LED has to be pinned to a clock.** Each LED's CSS animation starts when its own state changes, so LEDs that flash would flash out of step. `paintLeds` sets
  `startTime = 0` on the animations after a flashing LED changes, and a test samples two flashing LEDs for two periods. Without it the hardware's one blink becomes several.
- **Space on a `<g role="button">` scrolls the page** unless the key's default is prevented, and a screen reader's Activate arrives as a click with `detail` 0, which a pointer's click
  never has. Both are handled and both have tests; neither was caught by the first mutation run.
- **Stamps in the real app:** six runs, 46 to 48 sends each, every send stamped at least 59.6 ms ahead of the moment it was made (median 65 ms, L is 30). The plan says "no earlier than
  `now + L`"; the test asserts "never late, and a median of at least `L`" so a busy runner cannot turn a head-start jitter into a failed test. The owner can tighten it.
