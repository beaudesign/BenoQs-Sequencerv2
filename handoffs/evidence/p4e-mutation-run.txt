P4e, mutation run over the S3 harness (spikes/s3/analyse.ts, format.ts, page.ts) and its tests (WENGE-0015).

WHAT THIS IS. 53 single-line changes, each made to one source file in turn, the tests that cover it run, and the change put back. A mutant is
"caught" when a test fails (or the compiler rejects it); "survived" when every test still passes. A survivor is a line the tests do not
pin. Run by a hand-written script of string replacements that is not committed; each mutant is named by what it breaks, below.
The Node mutants (analysis and report, 0 to 37) run `node --test test/s3-analyse.test.ts test/s3-report.test.ts`; the browser mutants
(38 to 52) run `test/browser/s3.browser.test.ts` in headless Chromium. The first run was on the tree of 492a123 (the page, report and
runner as first committed); the re-run of the seven that survived or came out doubtful was on that tree with the tests named below added
(they were committed in 051f24a). The rest of 051f24a (the page's clock-map record, the stand-in's stamping, the start-up wait) was made
after the re-run, so the count below is for the tree as it was then, and not for the final head.

THE TWO THAT STAND, AND WHY (named, not hidden):
  [51] the follower is fed `seen` and not `stamp`. In the simulation the stamp is the page's own clock a fixed 2 ms behind the time the
       page saw the pulse (STAMP_AGE_MS in spikes/s3/stand-in.ts), and the follower, which only compares one pulse with the next and with
       its own estimate, has the same tempo and a phase 2 ms different; the figures it gives are inside what the tests allow for a stand-in
       with 0.3 ms of scatter. A test that tells the two apart needs a stand-in whose stamps and seen times differ by more than the tolerance
       AND a threshold that is not mine to set. This one is for the real run: the clock-domain line of the report (stamp against seen) is the
       measure, and a page that fed the follower the wrong one would show a different phase there. Passing this mutant is a limit of the
       simulation, not a finding about the page.
  [52] Start and Stop swapped in the page's own count. The send run sends exactly one Start and one Stop and the same table counts what was
       sent and what was heard, so a swap is invisible in a run that has one of each; mutant 37 (Continue and Stop swapped in the report)
       is caught, so the report's own order is pinned. An equivalent mutant for the run the test makes, not for a run with a Continue.

WHAT THIS SAYS ABOUT THE SUITE. 51 of 53 mutants are caught after the additions; the two that stand are named above with their reason.
It does not say the harness measures Live correctly. It says the code that reads the records does what its tests say, and that the page
puts the records down as the tests say; whether a real port's stamps are on the clock the follower assumes is the first line of the
owner's S3 report.
