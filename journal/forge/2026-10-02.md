## 2026-10-02

Task WENGE-0015, SPEC-0002 P4b. Hat: **Forge**, with a **Referee** hat for the baseline (`harness/baseline.txt`). Built on P4a (PR #29), so it
carries P4a's commits and the plan's (merge #27, then #29, then this).

**Intend to change:** put the second output port, the MIDI input path and the `?route=` stand-in for port 2 into the page, with no change to
`octocore`, and one additive export, `octoweb_set_track`.
**How I'll know it worked:** the plan's M1 and M6 hold in a Node test over the real scheduler and decoder and in the built app in Chromium with two
fake outputs and a fake input; M7 and M8 hold for everything that exists in P4b; a deliberate breakage of each new behaviour fails a test.

### What happened

- **First act (D-P4-9):** read the W3C text and tried to measure on a real port. The text says only System Exclusive is filtered, and does not
  name the clock of an incoming `timeStamp`; this Chromium cannot start Web MIDI at all (`NotAllowedError` without a permission,
  `InvalidStateError` with one, no MIDI backend). So the first half is read and the second is **not measured**: `specs/SPEC-0002/p4b-findings.md`.
- **The engine side:** `octoweb_set_track(track, attr, value)`, one shim, red first (7 compile errors, then 5 new native tests green), with its
  `ABI.md` row. The attribute numbers are the engine's list, and three tests pin them (Rust, Node reading `ABI.md`, `TRACK_ATTR`).
- **The page:** `src/midi-in.ts` (decode, count, `InputPath.onMessage` empty), `src/route.ts` (parse text only), `src/midi-access.ts` (inputs, a
  `failed` status), the strip (MIDI Out 1, MIDI Out 2, MIDI In, five Tab stops), `pages/app.ts` (the one reader of the address).
- **Tests:** 152 Node (up from 114, plus the browser-side helpers), 37 Chromium (up from 26), 5 + 2 new native tests. `cargo xtask verify`: 4 pass,
  0 fail, 6 not_implemented; assertions 462, baseline 455 to 462.
- **Mutation run:** 42 deliberate breakages, all caught (`handoffs/evidence/p4b-mutation-run.txt`). One survived the first run: nothing asserted
  that channel 16 is port 1 and 17 is port 2 in the strip's sentence. A boundary test closed it.

### What I learned and what surprised me

- **A platform failure was being called a refusal.** The real browser's `InvalidStateError` hit the old catch-all and told a person to "allow it for
  this site". Found only because the container's Chromium fails that way. It now says it could not start and gives the browser's reason.
- **`setOutput` cleared every device's ordering memory.** Invisible with one port, a latent break of ADR-0008 amendment 1's rule 1 with two,
  because the page re-applies both ports on any change. Fixed and tested.
- **The browser tests passed the first time they ran.** They were written before the code but not run red (the modules did not exist), so a pass
  proved nothing by itself. The mutation run is what shows each can fail, and it is why the run is in the evidence and not just the count.
- **No colour, length or type size and no numeric literal was needed** in the strip or `app.ts`: the 500 ms redraw interval lives in `settings.ts`.
  The slop rules passed without change.

### Departures and defaults, flagged

- **M7 and M8 are met in part.** The clock-state control is not in P4b: master needs P4c and slave needs P4d, and a control that does nothing
  must not be shown. It arrives with them. (The plan listed M7 and M8 under P4b; this is a smaller P4b, said first in the pull request.)
- **The route's track is 0 to 9, the matrix row,** as the control ids give it (`matrix.r3.c1` is track 3), and the channel is the engine's 1 to 32.
  The plan's example `?route=3:17,4:18` did not say whether tracks count from 0 or 1. A default; one line in `src/route.ts` and the README to change.
- **Labels are "MIDI Out 1", "MIDI Out 2", "MIDI In"** (the manual names "MIDI Out 1", "MIDI IN 1/2", "port 1/2"; one input, not two, as the plan
  accepted).
- **`STATE.md` is not edited here.** Its P4 section is in #28, which this branch does not carry; editing it here would conflict. It needs one line
  when P4b merges.

## 2026-10-02, later: P4c, the page half

Task WENGE-0015, SPEC-0002 P4c. Hat: **Forge** (octoweb, the page, the scheduler) with the **Referee** hat for the baseline. The engine half is the Metronome's, in
the commit before this one (`journal/metronome/2026-10-02.md`). Built on P4b (#30), so it carries P4a's and P4b's commits.

**Intend to change:** put the engine's clock in front of the page: ABI 2 (event kind 5, `octoweb_set_clock`, `octoweb_tick_position`), the merge of the clock into the events
by sample, and a scheduler that sends each clock message to every chosen device once.
**How I'll know it worked:** native tests through the exports (`abi_clock.rs`, 14) pin the record, the order and the buffer; Node tests over the real worklet, wiring and
scheduler (`clock-path.test.ts`, 6, and the scheduler's 12) pin what reaches a device and when; three Chromium tests do the same through the real AudioWorklet; a deliberate
breakage of each new behaviour fails a test.

### What happened

- **Red first, twice.** The web module's tests ran against inert stubs (12 failing, 3 passing by construction), the page's against the P4b module and sources (17 failing,
  3 passing by construction): `handoffs/evidence/p4c-abi2-red.txt`, `p4c-page-red.txt`.
- **ABI 2:** kind 5 in the existing 12 bytes, the events buffer 512 records, `octoweb_set_clock`, `octoweb_tick_position`, the merge (`encode::write_merged`, realtime first
  on a tie, four unit tests). The worklet takes a `clock` message; `Host.setClock`; the wrapper's `setClock` and `tickPosition`.
- **The scheduler:** a realtime message goes to every distinct chosen device, once; it is counted in `stats.realtime` and not in `sent`; rule 1 (timestamps never go
  backwards) holds across notes and clock together; `onSend` names it with port 0.
- **Tests and gates:** 178 Node (152 before), 40 Chromium (37 before), 14 + 4 new native tests; `cargo xtask verify --base origin/main`: 4 pass, 0 fail, 6 not_implemented;
  assertions 503 (baseline 462, 42 added, 1 removed under ADR-0009).
- **Mutation run:** 44 deliberate breakages across the engine, the module and the page, all caught after one survivor (in the engine) was closed (`p4c-mutation-run.txt`).
  Planning it showed that nothing asserted `Host.setClock(false)` turns the clock off, which the page's own tests could not reach (`Host` needs an AudioContext), so a
  Chromium test was added before the run.

### What I learned and what surprised me

- **A defect in my own test support, found by a test that read both devices.** `Session.advanceOutputs` advanced each fake output from where the last one had moved the
  shared clock, so port 2's deliveries were logged late. Every earlier test read only port 1. Fixed in `test/support/session.ts`; mutation T16 holds it.
- **My ABI test expected a Clock on the Continue's sample.** It cannot be: a resume is between pulses, and the engine puts the next pulse on its grid. The test now says
  "less than one pulse later" and the README and ABI.md say the same.
- **Nothing in the page turns the clock on yet.** That is deliberate: the control belongs with the follower in P4d, and a switch that sends a clock nobody can stop from the
  strip would be a half. The README says so in bold.

### Departures and defaults, flagged

- **M3 stays `pending` on D0**, and amendment 1 gives a second reason a pattern is not on the receiver's grid (the first note is 11 ticks after Start).
- **M7 and M8 are still met in part**, as P4b said; the clock-state control arrives in P4d.
- **`stats.realtime` is new and `sent` keeps its meaning** (notes and controllers), so S1's analysis is unaffected.
- **The scheduler sends the clock to every chosen device, even one that is also a note device.** ADR-0009 decision 3, as written. A per-port choice is a P4d question.
