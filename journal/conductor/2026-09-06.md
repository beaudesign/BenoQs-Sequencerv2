## 2026-09-06 (later, same day) — octoffi

**Intend to change:** Start `crates/octoffi` now that `octocore`'s public API
(`Engine`, `Command`, `Event`, `RenderContext`) has landed and stabilized
enough to wrap. Conductor-owned per ROLES.md, so picking this up rather than
leaving it for whoever wears this hat next.
**How I'll know it worked:** a real C program compiles against a hand-written
`octoffi.h`, links against `liboctoffi.dylib`, and calls through into
`octocore` correctly — not just Rust-internal `cargo test`.

### What I did

Thin wrapper: `octocore_engine_new/free/handle_command/render/is_running`,
all taking an opaque `*mut Engine`. `Command`/`Event` cross the boundary by
value since both are already `#[repr(C)]` in octocore. Hand-wrote
`octoffi.h` (no `cbindgen` install attempted — no network reliance wanted for
something this small) as a C tagged-union matching the Rust enum layout.

Verified for real, not just asserted: wrote a throwaway C smoke test, compiled
it with `clang` against the built `liboctoffi.dylib`, ran it. Play/Stop
correctly toggled `is_running` through the hand-written header's tag/union
layout — if the discriminant ordering or union layout guess had been wrong,
this would have shown wrong behaviour (or crashed) rather than silently
passing, since it's real linked code, not a mock.

### What I learned

Rust `#[repr(C)]` fieldful enums really do lay out as a plain C tagged union
(tag first, discriminants in declaration order) — this was a guess until the
C smoke test proved it against this specific toolchain/platform (arm64
Darwin). Worth re-verifying if this ever needs to work from Swift too, since
`cbindgen` (once available) removes the by-hand transcription risk entirely.

### What's now blocked / next

- `octoffi.h` is hand-maintained — will drift the moment `octocore`'s
  `Command`/`Event` change shape. Whoever touches those types next should
  update this header in the same commit, or get `cbindgen` installed first.
- No Grid-mutation surface exists over FFI yet (only `Command`, which has no
  step-editing variant) — a Swift caller can start/stop transport and render
  audio, but can't yet program a pattern through this boundary. Needs either
  new `Command` variants or a separate `octocore_grid_*` accessor surface;
  deferred rather than guessed at, since the real interaction model belongs
  to `panel.truth.json`'s `ControlId` scheme, which doesn't exist yet.
- The C smoke test itself was not kept in the repo (ad hoc, run manually
  outside `cargo test`/`just`) — if this boundary needs to stay verified
  automatically, it should become a real `just verify-arch` step later
  (docs/07-verification.md already names `verify:arch` for exactly this: "FFI
  declaration agreement between Rust and Swift").
