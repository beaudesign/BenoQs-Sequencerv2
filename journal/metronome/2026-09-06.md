### What I did

Installed the Rust toolchain (none was present) and `just`. Read
`archive/v1-max4live/octopus_{engine,data,scale}.js` as the only prior working
implementation (`archive/v1-cpp-juce`'s port has no chains/effector/hypersteps

Wrote the domain model, the tick loop, and the fixture DSL runner. Wired
`just verify-octocore` and `just verify-conformance` for real (they were
honest stubs from this session's earlier bootstrap pass).

### What I learned

`Grid` (ten `Bank`s deep) is about 1MB as a plain value type. Constructing it
as a stack temporary overflowed the test harness's thread stack — not a
logic bug, a size-of-type problem. Fixed by heap-backing only the outermost
`banks` array (`Vec<Bank>`); everything below `Bank` stays a fixed-size
`Copy` struct on purpose, because `Page` (~6KB) is what the engine actually
copies once per tick, and that copy needs to stay cheap. This is the one
place this crate isn't `no_std`-clean yet.

Two independent prior implementations (the archived JS and the archived C++
port) agree with each other on the direction-4/5 assignment (4 = biased
random walk, 5 = uniform random) but *disagree* with the new doc's own prose
ordering ("random, brownian" as written implies 4 = random). Went with the
two agreeing prior implementations over the un-cited prose — logged in
AMBIGUITIES.md rather than silently picking one.

Also learned, the hard way, that "one tick" and "one step" are not the same
thing when writing the fixture-DSL `play N step` directive — a step is
`DEFAULT_STEP_TICKS` (12) ticks at the default multiplier, and my first pass
at the runner called the tick function once per "step", which fired nothing.

### What's blocked

Phrases, hyperstep, and step-events are real data models with working
resolution/carry functions but aren't wired into the note-firing path — doing
that correctly needs either the real manual or a real `panel.truth.json`
(neither exists), so guessing at the wiring felt worse than leaving it as an
explicit gap. Six ambiguities logged, all provisional against the archived
priors rather than a manual citation. `docs/03-sequencer-core.md` §1's
per-constant `Ref:` citation requirement genuinely cannot be met yet — this
blocks getting past ~20 conformance fixtures (target is ≥250 by Phase 3) no
matter how much more of this crate gets built, until someone supplies
`reference/manual/`.

### What I did

Ingested the manual (page-indexed, `just manual <topic>` wired for real) and
the photo (topology-check notes only, no truth-file fabrication) — see
`journal/panelwright/2026-09-06.md` for that half. Then worked through the
whole `octocore` surface against the real text: cited two tables that turned
out already correct (GRV, strum); fixed default track pitches (octave *and*
direction both wrong); rewrote the effector (added MCC, listener gating,
post-modulation publish for listening-feeders, the Listener Step Mask); fixed
chord polyphony's rest-padding algorithm; replaced FLT's wrong boolean-attribute
model with the real multi-track merge operation; fixed phrase types (Reverse
was a no-op bug, RandomAll invented fake data); replaced hypersteps' wrong
hold-to-apply model with the real persistent-link one; rewired step events
with real AMT/Range addressing for Track Toggles and additive (not
overwrite) semantics for DIR/POS/MCH, plus revert-on-stop and
on-the-measure deferral; and replaced custom directions' "fall back to
random" placeholder with the real 16-slices-of-triggers mechanism. 17 commits,
`just verify` green after every one, test count went from 21 to 43+2.

### What I learned

The bundled 2007 tutorial series at the back of the manual PDF (a separate,
differently-footnoted document folded into the same file) directly resolved
a design question the main chapters left ambiguous — whether multiple
triggers in one custom-direction slice fire simultaneously or one-per-visit.
The tutorial's own worked example ("that track will be 4 steps behind the
rest of the sequence") only makes sense if it's one-per-visit. Worth
remembering that appendix/tutorial material can outrank a plausible reading
of the main text, and that `pdftotext -layout` gives cleaner, more precise
extraction than reading page images — several of the "needs a follow-up
image read" items from the original plan turned out to be directly
extractable as plain text once I actually tried.

Also: the PDF's own page count and the manual's printed footer numbers are
offset by 2 (front matter), and I nearly baked that bug into the whole
`reference/manual/pages/` index before catching it by cross-checking a
known section (effector, p.59) against what actually landed at the naive
"page 59" file.
