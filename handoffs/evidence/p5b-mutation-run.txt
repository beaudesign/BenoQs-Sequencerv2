P5b mutation run, 2026-10-03. Hat: Panelwright.

What: 20 deliberate one-line breakages of the P5b code, one at a time, each run with
`cargo test -p octoface --no-fail-fast`. The mutants are in handoffs/evidence/p5b-mutate.py (set WT to the
worktree). A mutant is caught if the run fails and the code compiled.

Read this first: my first run used `cargo test -p octoface` without --no-fail-fast. Cargo stops at the first
failing test binary, and the unit tests run before the fixtures, so for K1, K2, K5, K6 and K7 only the unit
test was named and the fixtures looked as if they had caught nothing. With --no-fail-fast every layer reports.
The numbers below are from that second run.

Not tried: removing the `PanelMode::Step` half of the guard in `knob_turn`. It is an equivalent mutant: the
controller holds a zoom exactly when it is in Step mode, so the guard on the zoom alone behaves the same.

Which layer catches what, by design:
- The knob's direction, attribute, step, track, command count, detent count and the view's four reads
  (K1 to K3, K5 to K8, K11, V1 to V4, L1) are caught by the asserting fixtures in
  tests/conformance/panel/step_attributes/, and for K1, K2, K5, K6 and K7 also by the unit test that asks for the value.
- What the manual does not say and the controller does (a turn outside Step zoom does nothing, a zero turn
  and a press of a knob send nothing, an overflow is not a panic: K4, K9, K10, K12) is caught by unit tests only.
  No fixture asserts it, on purpose (Q41).
- The runner's own directives (R1 to R3) are caught by the runner's tests and by the fixtures that use them.
