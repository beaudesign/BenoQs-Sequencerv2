## 2026-09-29

**Intend to change:** Make Stop, Reset and Play safe under a host (SPEC-0001 O1 and O2), and
give the fixture DSL the sample-domain vocabulary to say so (O9), without changing any
musical behaviour the manual cites.
**How I'll know it worked:** the new invariants and fixtures fail on `6ef921f` and pass now;
every existing test still passes; the stress probe is unchanged within noise and still makes
0 allocations.

### What I did

- DSL v2 (`fixture.rs`): `bpm`, `samplerate`, `play/stop/reset`, `render N buffers|s buffer=M`,
  `expect event on|off|cc ...`, `expect balance`. Tested as a language, not as an engine.
- Wrote the failing tests first: 4 fixtures under `tests/conformance/transport/` and 8 property
  tests in `crates/octocore/tests/invariants.rs`. On `6ef921f`, 6 of 8 invariants and all 4
  fixtures failed for the intended reason.
- O1: sounding table, flush on Stop/Reset, resumable across renders, one NoteOff per NoteOn owed.
- O2: `next_tick_due = sample_clock` on the stopped-to-running transition.
- p.94: a Stop while stopped sends CC 123 on 32 channels. Logged in AMBIGUITIES.

### What surprised me

- **A retriggered pitch defeats a single NoteOff.** My first flush sent one NoteOff per
  (port, channel, note). The property test found seeds where the same pitch had been started
  six times while still ringing. Fixed by sending one per NoteOn owed.
- **Ports and channels are 1-based** in `RawEvent` (ports 1 and 2, channels 1 to 16). My scratch
  probes had assumed 0-based. The table indexes with a range check so a stray value cannot
  index out of bounds.
- **The first note of a pattern fires 11 ticks after Play**, not on the first tick. Not a bug I
  can call without the manual, so the tests do not depend on it. Worth a look by whoever owns
  the step accumulator (O4 will touch it).
- **My "24% of budget" worst case was one lucky run.** Re-measured: the maximum swings 0.9 to
  3.8 ms between identical runs on both the old and new engine, so it is scheduler noise in a
  shared container. Corrected in `specs/SPEC-0001/findings.md`. p99.9 is 4.3% to 8.0% of budget.

### Blocked or open

- Q5 is only half settled: the manual is silent on the first Stop (see AMBIGUITIES). Retrigger
  behaviour (implicit NoteOff or overlap) is O10, not done here.
- Legato mode (p.16) is unimplemented. Not in SPEC-0001. Filed in AMBIGUITIES.

## 2026-09-29, PR 4 (timing and emission)

**Intend to change:** Make the timing of emitted events independent of the host's buffer size
(O3), stop the engine dropping events silently and stop a bad tempo from killing the clock
(O5), and fix what the engine emits: ordering, velocity 0, bender and pressure (O10).
**How I'll know it worked:** each new test fails on the commit before its fix and passes
after; `cargo xtask verify --base metronome/transport-safety` exits 0 with nothing lost from
the baseline; the allocation probe still reads 0.

### What I did

Three commits, one per task, each preceded by its failing tests (red runs saved in the
scratchpad and quoted in the handoffs).

- O3: `render` steps ticks `MAX_EARLY_TICKS` (12, the STA table's reach) ahead. On `e04d9ba`
  192 of 192 (seed, buffer) pairs differed from the 512-sample run. Now none does.
- O5: events that do not fit in the caller's buffer wait for the next call (`EventBuffer::with_limit`
  lets the FFI pass its real capacity). A note is queued as a NoteOn and NoteOff pair or not
  at all. A tempo outside 1 to 999 BPM runs no tick and leaves no backlog. Big host buffers
  are handled in 1024-sample chunks. `Diagnostics` counts each of these, readable over the FFI.
- O10: the queue is a binary heap keyed (sample, off < controller < on, creation number), so
  the order events leave in is total. A note at velocity 0 is not transmitted (manual p.40).
  Bender and channel pressure tracks now send `PitchBend` (`step << 7`, manual p.91) and
  `ChannelPressure`. DSL v3 gained `track T vel|mcc` and `expect event bend|pressure`.

### What surprised me

- **My first buffer-size test failed for the wrong reason.** `Event` carries a buffer-relative
  `at_sample`, so streams from different buffer sizes never compared equal. The test had to
  zero it. The red run before that fix said "every event differs", which was noise, not a bug.
- **An infinite tempo hangs `render`.** Zero samples per tick means the tick loop never
  reaches the end of the buffer. Found by reading, confirmed by a test that timed out at 30 s
  on the parent commit.
- **Tempo 0 kills the engine for good, not for a buffer.** `next_tick_due` became infinity and
  nothing ever moved it. Hosts report tempo 0 before playback starts.
- **The retriggered NoteOff ordering bug was hiding behind the sample rounding.** A NoteOn due
  at 100.3 and a NoteOff due at 100.7 land in the same sample, and ordering by the raw time put
  the NoteOn first, so a receiver would end up silent. The sort key uses the whole sample.
- **The heap is cheaper per event. The "8.9 us to 2.8 us" I first wrote here is withdrawn.**
  The old queue scanned all 512 slots for every event, so the heap should win, but the two
  probes used different scenes, and on the dense scene the new engine refuses about two thirds
  of the notes (`queue_overflows` 230,708 in 10 s, `queue_high_water` 512), so it does far less
  work. Independent review found this. It is not a like-for-like comparison and must not be
  quoted. A like-for-like number needs one committed scene that neither engine overflows.
- **A fixed queue capacity did not survive a 16,384-sample buffer.** Chunking fixed the queue,
  but the 256-event output cap still binds for dense patterns above about 4,096 samples. The
  events are deferred, not lost. Raising the cap changes a public constant, so I did not.

### Blocked or open

- Retrigger, bend mapping, velocity-0 reading, Stop and the bender, and lookahead trade-offs are
  in AMBIGUITIES with both readings. None needs a real Octopus to unblock except the first Stop.
- O4 (clock) and O6 (command ring) are high tier or unapproved and are not started.

## Review follow-up (WENGE-0011)

**Intend to change:** act on the independent review's finding 4 and the small Metronome-zone
nits, without touching pushed history. **How I'll know it worked:** a heavy chord pattern uses
under half the event queue; the runner warns when notes are refused; new tests fail before.

- **The stress scene was overloaded and my timings hid it.** The dense scene refuses about two
  thirds of its notes (`queue_overflows` 230,708 in 10 s at 512 slots). The chords-only scene does
  not overflow but used 410 to 430 of the 512 slots. `tech.md` says the queue holds 1,024. I set
  it to 1,024 and committed both scenes as tests. The dense scene still overflows at 1,024, on
  purpose: it is the overload scene, and the test asserts overload is counted and refuses
  whole notes.
- **Tests that found nothing.** A host that changes its buffer size on every call, and a
  one-sample host, both pass on the parent engine. They stay as coverage.
- **`Played` now carries `Diagnostics`** so `octorun` can warn. A golden hash of a stream with
  refused notes would lock in a wrong performance, so a test asserts that no example refuses,
  defers or delays anything.
- **`play 400000000 step` panicked** with a multiply overflow in a debug build. It is an error
  now, and counts above 100,000 steps are refused.

### Blocked or open

- What the sequencer should do when a real pattern overloads the queue is a product decision.
- The lookahead assumes a constant tempo. Not fixed, listed in the handoff.

## O6: command ring and snapshot (WENGE-0006)

**Intend to change:** give the engine a way to be edited and watched from other threads
without a lock, an allocation or a data race: a command ring in and a snapshot buffer out,
plus `SetTrack` and `SetStep` commands and an additive C surface. **How I'll know it worked:**
every test in `specs/SPEC-0001/o6-test-plan.md` fails on a stub and passes on the build;
loom passes on the small models and fails when the code is broken on purpose; a two-thread
soak sees no torn command or snapshot; an engine with no link is byte-identical to before
(golden streams, determinism gate, E3); render, push and claim allocate nothing.

- **The plan came first** (`842aeb9`) and recorded the choices it made inside the owner's
  approval. The build disagreed with it in a few places and section 10 of the plan says where.
- **`unsafe` stayed out of `octocore`.** A ring and a triple buffer are normally `UnsafeCell`.
  `docs/02` §3 keeps `unsafe` for `octoffi` and the renderer, so the slots are atomic words and
  the types are encoded to words and back. It costs an encode step and about 0.7 microseconds
  per snapshot. It also means a wrong protocol shows up as a wrong value, which the soak and
  loom can see, instead of as undefined behaviour.
- **`docs/02`'s triple-buffer protocol cannot work as written.** A writer that only `store`s
  cannot know which slot the reader holds. The swap-based buffer is the standard fix and is
  what was built. A request goes to the Scribe.
- **The ring overwrites.** The producer never reads what the consumer writes, so a full ring
  cannot make it wait; a lapped consumer skips ahead and counts what it lost. Each slot has a
  seqlock stamp so a slot overwritten mid-read is dropped, not returned half old and half new.
- **Loom found nothing wrong with the code, and I wanted to know it could.** The mutation
  script breaks it seven ways. Making the *final* stamp store `Relaxed` is an equivalent
  mutant (the head counter's own release already orders it), which I first wrote as a real
  one; the script keeps it as M8, expected to survive, so the reasoning is on record.
- **Two of my tests were wrong, not the code.** C4 and C6 rendered too few buffers to hear
  anything: a fresh engine decides its first note in the first render, but it sounds about
  1,375 samples later. Corrected without touching the engine, and noted in the red file.
- **Found and not fixed.** `RenderContext::playing` overrides `Play` and `Stop` commands (added
  to `AMBIGUITIES.md`; it is O4's question). An edit is heard no sooner than the next render
  and 12 ticks of lookahead have already been decided: about 31 ms at 120 BPM against
  `docs/02` §6's 1.3 ms. `Command` crosses the C ABI by value, so a bad tag is undefined
  behaviour. The direct setters race a running render. `rustfmt --check` has 396 diffs at the
  parent.
- **What surprised me.** The snapshot is 8,408 bytes, not 6 KB, and adding the link cost only
  0.7 microseconds a render; applying 256 SetTrack commands about 7 (256 Resets about 64; the review asked for that check).

- LEDs and encoders in the snapshot wait for `panel.truth.json`.
- O4 is a separate approval. Its release plan is `specs/SPEC-0001/o4-release-plan.md`.
