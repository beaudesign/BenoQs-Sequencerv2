## 2026-09-30

Task WENGE-0013, SPEC-0002 P2b. Three hats, worn one after the other and named in each commit:
**Conductor** (the contract files ADR-0007 authorises), **Panelwright** (`octoface`, the fixtures),
**Referee** (the `conformance` gate and the baseline).

**Intend to change:** give `ControlId` a meaning (`contracts/controls.json`), and build `crates/octoface`,
a panel controller that turns a matrix press into the right engine command and LED frame for five
workflows: Page mode step toggle, Step zoom, ESC, the EDIT cycle and the PLAY LED (spike S5).
**How I'll know it worked:** 37 panel fixtures, written and committed red before the controller
existed, pass against it; 11 more fixtures exist for what the manual leaves open and assert nothing;
hand-made breakages of the controller are caught by those fixtures; `cargo xtask verify --base origin/main`
passes with the assertion count above 310.

### What I did

- **Contract (Conductor hat).** `contracts/controls.json`: 244 controls numbered from the manual's own
  grid (matrix 160 + 16 × row + column - 1, and a block of 16 per zone), each cited to manual pages;
  anything the manual does not settle is `pending` with a question number, and whole groups whose
  count the manual leaves open are in `open` with no number. `contracts/controls.schema.json`.
  `panel.truth` and `motion.registry` schemas moved to `archive/native-panel/contracts/`;
  `verification.report.schema.json` lost the photoreal vocabulary (ADR-0007 decision 3).
- **Crate (Panelwright hat).** `crates/octoface`: no runtime dependencies. `Panel::input` returns
  engine `Command`s and `Intent`s (requests for engine capabilities that do not exist yet);
  `Panel::leds` returns a 512-slot LED frame. The tests load `controls.json`, validate it against its
  schema and fail if the controller names a control the file does not hold.
- **Fixtures.** `tests/conformance/panel/**/*.panel`: a small script (`given`, `at N ms press|release|click`,
  `expect led|mode|engine|command|intent`). Commands are applied to a real `octocore::Engine`, so a
  fixture asserts what the engine ends up holding, not only what the panel said. 37 assert; 11 are in
  `pending/`, each with `# pending:`, `# manual:` and `# question:` headers.
- **Gate (Referee hat).** `conformance` counts `.panel` files, requires the `panel_fixtures` binary and its
  `all_panel_fixtures_pass` test when any exist, reports the pending count (not floored) and fails a pending
  file with no headers or with script lines. A tightening. Baseline: 337 tests + 48 fixtures = 385 (was 310).

### What surprised me

- **The engine boots in `Mode::Grid`.** The panel's first view is Page (p013, p014). The controller sends
  `SetMode` on each transition, so the two disagree until the first one. Filed as a request.
- **"Play" is at least two keys.** The MODE block's PLAY (p066) and the transport's Play (p016, p049) may be
  one control or two. S5 says "PLAY LED"; I built p066 (the mode key with the snapshot behaviour) and
  left the transport LED pending (Q21, Q26).
- **Three of my own expectations were wrong, and the controller was right.** After the controller was green,
  `esc_leaves_step_zoom`, `the_page_button_leaves_step_zoom` and `the_zoom_key_leaves_step_zoom` expected a
  press on step (3,5) to set it, but the step had been switched on earlier in the same script, so the press
  correctly clears it (p068: "the step buttons toggle the step states"). I re-derived each from the page before changing it, and
  the fix adds `expect engine step` and `expect led` lines so the script now pins both sides. A reviewer
  should look at this change in `5971111`, because it is the shape of "fit the test to the code". It is not:
  the page's rule gave the answer and the old expectation contradicted it.
- **Some fixtures were vacuous** at first: they passed against the stubbed controller because what they
  expected was already the default. Found by running them against the stub, and fixed before the red commit,
  so the red commit shows all 37 failing.
- **A generator script overwrote a hand-edit** of `controls.json` once. The generator now carries the edit.
  The generator lives in my scratch directory and is not committed: the file is the contract.

### The independent review, and what I did with it

A fresh read-only agent reviewed the branch: approve with changes, no blocker, twenty findings. I checked each
against the manual before acting. Fixed: LED flags the manual does not give (PAGE, the MIX rotaries, the
transport Play, Stop and Pause keys: dropped; `led` absent now means "not stated"); SCALE MOD, SEL and CAD were
missing (p020, p071); three fixture assertions the pages do not state (PLAY mode ending on Program or Stop,
a chord step's Page view LED) moved to pending as Q36 and Q37; Q38 (toggle on press or release) and the
provisional-choices list; the gate counting a `.panel` file the runner never reads (reproduced by the reviewer:
a failing fixture in `tests/conformance/elsewhere/` left the gate at pass); a test that would have failed when
someone closed a pending question; tutorial cites; a CODEOWNERS line; two wrong citations.
Declined or corrected: **ESC does have an LED** (p095, "the Green flashing ESC button"), so I added the
citation instead of dropping the flag. Not changed: repeated controls keep names like "MIX encoder, row 3"
(the row is an index, not a name; the schema says so now). Not built: `release_all` and the hold gestures
(Q24, Q38); the web app must release keys on focus loss (P3).

**A mistake of mine the review did not catch.** I had shared one `CARGO_TARGET_DIR` between this worktree and
a scratch copy used for mutation runs. Test binaries bake in `CARGO_MANIFEST_DIR`, so some of them read the
scratch copy's files, which is invisible while the copy exists. The earlier "all pass" figures were therefore
not proof for the worktree's own files. I deleted the target directory and re-ran everything from a fresh one:
the numbers above are from that run. Rule for next time: one target directory per tree.
